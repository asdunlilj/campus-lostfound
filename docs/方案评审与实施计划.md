# 校园失物招领系统 · 方案评审与实施计划

> **版本 v1.0（定稿）· 2026-11-08**
> 评审对象：C++ 后端 + MySQL + 现代前端 + 本机 Windows 服务器 + 局域网 + 手机/电脑实时交互。
> 依据：本机只读体检（附录 A）+ 三份 2026-11-08 时点核对的技术调研（附录 B）。所有版本号均已对官方源核实。

## 0. 结论先行（TL;DR）

### 0.1 一句话判断

**方向可行，但原始思路不能直接开工。** 有 4 个"硬伤"、6 个"欠定义"和 3 个"被低估的成本"。补足后可以在本机完整落地：演示版约 5~7 周（业余），完整可试用版约 10~14 周（业余），若换后端语言可省 6~8 人日。

### 0.2 四个硬伤（不解决必返工）

1. **网络可达性未验证**：校园 Wi-Fi 常见客户端隔离（AP Isolation）、跨 VLAN、Portal 认证；手机未必能访问你的笔记本。这是"本机服务器"方案的生死线，必须第一天用 5 分钟实测（§7.1）。
2. **HTTPS 缺失会让手机端大面积残废**：http://192.168.1.100 不是浏览器安全上下文（secure context）→ **PWA 安装、Service Worker/离线、通知、getUserMedia 自建相机全部不可用**；https 页面里的 ws:// 还会被当混合内容拦截 → **实时必须 wss://**。
   - 补充澄清（调研核实）：input type=file accept=image/* capture 拍照在 HTTP 下**可用**，所以 M1（未上 HTTPS 前）能先做拍照上传；但 PWA/离线/通知/自建相机仍必须 HTTPS。
   - 另外，**任何公共 CA 都不会给 10.x 内网 IP 签证书** → 证书方案是必答题而非可选项（§7.3）。
3. **认领业务规则与并发未设计**：失物招领的难点不是 CRUD，而是"**防冒领**"和"**一物多人同时认领**"。必须状态机 + 事务 + 数据库唯一约束（§5.2）。
4. **单机运维与备份缺失**：本机是**笔记本 + 仅无线**（实测空闲内存一度只有 1.66GB、交流电下 3 小时自动睡眠）；断电/睡眠/Windows Update/Insider 强制重启 = 服务全断；数据只在本地 = 一次故障全丢。必须服务化、自启、健康检查、每日备份（§7.4/7.5）。

### 0.3 六个欠定义（开工前必须定）

需求边界、数据模型、API 与实时事件契约、实时语义、安全模型、验收标准。本文 §1/§5/§6/§8/§10 给出可直接采用的版本。

### 0.4 关键事实基线

| 项 | 实测 / 核对结果 |
|---|---|
| 服务器 | LENOVO 笔记本：Ryzen 5 5500U（6C/12T）、13.85GB 内存、C 盘剩 50GB / D 盘剩 90GB |
| 网络 | 仅 WLAN 连校园 Wi-Fi（Open 认证、192.168.1.100/24、网关 192.168.1.1、被 Windows 识别为"公用"网络、防火墙全开）；ACME 出站 443 可达 |
| 开发环境 | **C++/前端工具链全部缺失**：无 MSVC/CMake/vcpkg/Node/pnpm；MySQL 8.0 已安装但服务 Manual/Stopped |
| 数据库 | **MySQL 8.0 已于 2026-04-30 EOL**，装环境应直接换 **8.4 LTS（至 2032-04）或 9.7 LTS（至 2034-04）** |
| 端口 | 80/443/3306/5173/8080/8443 均空闲；但校园网可能拦截 80/443 入站（需实测） |
| 技术基线 | 后端 Drogon 1.9.14 + libmariadb 3.4.11；前端 React 19.3.1 + Vite 8.3.6 + TS 6.0.3；反代 Caddy 2.11.9；服务壳 WinSW 2.12.0（详见 §4.9） |
| 成本真相 | 同功能 MVP：C++ 后端约 15.5~20 人日，Go/Node 约 10~12 人日 → **C++ 多 5~8 人日（+45%~70%）**，不熟再 +3~5 人日 |

### 0.5 建议的流程重排（你原来的隐含顺序是"选技术→写后端→写前端→联调→上手机"）

~~~
0. 网络可达性实测（0.5 天，先做，决定方案是否成立）
1. 需求边界 + 业务规则 + 数据模型（1 天）
2. API 契约（OpenAPI）+ 页面清单（1 天）
3. 环境搭建 + 服务骨架 + 1 天技术验证 spike（3~4 天）
4. 一条垂直切片：注册→登录→发布→列表（2 天）
5. 核心业务闭环：认领/审核/取件/完成（5~7 天）
6. 图片上传 + 搜索 + 通知 + 实时（4 天）
7. PWA + HTTPS 证书 + 安全加固 + 移动端适配（4 天）
8. 备份/运维/压测/验收（4 天）
~~~

理由：先把"方案是否成立"和"技术是否走得通"两个最大不确定性引爆，再投入业务开发；契约先行让前后端可并行，避免"后端写完等前端"的返工。

## 1. 先定义问题：这个系统到底要做什么

原方案跳过需求定义直接进技术，这是最容易被低估的不足。失物招领表面是"发帖 + 列表"，实际业务规则比想象的多。

### 1.1 角色

| 角色 | 说明 | 权限要点 |
|---|---|---|
| 学生用户 | 失主 / 拾得者（同一账号，两种身份） | 发布、浏览、搜索、认领申请、管理自己的帖子 |
| 管理员 | 学生会/保卫处/指导老师（1~3 人） | 审核、下架、查看完整联系方式用于线下协调、处理举报、导出统计 |
| （可选）楼宇管理员 | 宿舍/图书馆值班室 | 只看本区域帖子，无全局权限 |

**不要做"普通用户能看所有人手机号"的设计**——这是校园项目最常见的隐私事故。

### 1.2 核心用例（MVP 必须全部可用）

1. 学生用**学号 + 邀请码**注册，登录后发布"我丢了 X"（寻物）或"我捡到 X"（招领）。
2. 帖子包含：类型、标题、描述、分类、地点、时间、照片（1~3 张）、联系方式策略。
3. 所有人可按分类/地点/关键词/类型筛选，按时间倒序浏览；支持"只看未认领"。
4. 失主看到招领帖 → 提交**认领申请**：回答拾得者设置的核验问题 + 留言。
5. 拾得者/管理员**审核** → 通过后生成**一次性取件码**（24h 有效）。
6. 线下交接：拾得者核销取件码 + 失主确认 → 双方都确认后完成，帖子归档。
7. 全流程有**站内通知**，手机和电脑**实时看到状态变化**。
8. 管理员可下架违规/不实信息、处理举报、查看统计、管理邀请码。
9. 过期自动下架：发布 30 天后归档（可续期一次），到期前 3 天提醒。

### 1.3 "实时交互"的明确语义（原方案最含糊的一点）

| 交互 | 是否需要实时 | 实现方式 | 说明 |
|---|---|---|---|
| 新帖子出现在列表/匹配提醒 | 是（秒级） | WS 事件 + 列表局部刷新 | 手机发、电脑立刻看到 |
| 认领申请、审核结果、取件码 | 是（秒级 + 通知中心） | WS 事件 + 站内通知 | 关键链路 |
| 未读数多端同步 | 是 | WS + REST 拉取 | 手机已读，电脑红点消失 |
| 同一用户多端登录状态 | 是 | WS 事件 | 次要 |
| 站内聊天 | **MVP 不做** | — | 需要消息存储/已读/审核/限流/举报，工作量翻倍；用"认领留言 + 通知"代替 |
| 手机锁屏/后台推送 | **不承诺** | 以后可选 Web Push | 浏览器后台会挂起 WS；iOS 限制多；MVP 用"回到前台自动补偿同步" |

### 1.4 规模与非功能目标（写进验收）

| 指标 | 目标值 | 说明 |
|---|---|---|
| 注册用户 | 5,000（3 年累计） | 校园单校区规模 |
| 日活 / 峰值并发 | 500 / 50 | 一台普通笔记本绰绰有余（压测目标 50 并发） |
| 日新增帖子 / 图片 | 100 条 / 200 张 | 图片压缩后 100~400KB/张 |
| 存储估算 | 数据库 < 2GB/年；图片 20~40GB/年 | **D 盘只剩 90GB，必须做归档策略**（§5.6） |
| API 响应 | 内网 P95 < 300ms | 搜索 < 500ms（1 万条数据） |
| 前端质量 | LCP ≤2.5s、INP ≤200ms、CLS ≤0.1；首屏 JS gzip ≤250KB | 见 §10.3 完整指标 |
| 实时事件端到端 | 前景态 P95 < 1s | 断线重连成功 ≤3s、成功率 ≥99% |
| 可用性 | 教学演示/小范围试用 99%（约每周停机 <2h） | 笔记本+校园网达不到 99.9%，如实说明 |
| 备份 RPO / RTO | 数据 ≤15 分钟（binlog）/ 恢复 ≤2h | 至少日备；见 §7.5 |

### 1.5 关键业务规则（必须写进代码和测试）

- **防冒领**：认领申请必须回答拾得者设置的 1~2 个核验问题（如"物品内部有什么特征"），由拾得者确认；通过后发放一次性取件码；线下核销；双方确认完成。
- **一物一认领**：同一帖子同一时间只能有一个有效认领（pending/approved）；其余申请进入失败提示。用数据库唯一约束保证（§5.2）。
- **防重复发布**：同用户 24h 内相似标题 + 同地点 → 前端提示"可能重复"，允许继续但通知管理员。
- **审核策略**：先发后审 + 举报入口 + 管理员下架；**禁止上传含人脸/证件的照片**（页面明确提示"只拍物品"），管理员抽查。
- **联系方式**：默认不公开。平台内流转（认领申请/取件码）；管理员可见完整信息用于协调；公开页面只显示 张* / 138****1234 / 学号后 4 位。
- **过期与归档**：30 天自动归档（可续期一次）；完成后 7 天从公开列表隐藏；认领凭证类图片 30 天后删除。
- **权限隔离**：用户只能改/删自己的帖子；管理员操作全部写审计日志。

### 1.6 明确不做（MVP 范围外，避免无限膨胀）

聊天/IM、地图定位、扫码绑定、AI 图像识别匹配、微信小程序端、多校区多租户、积分/排行榜、物品保管仓库管理、支付/悬赏、人脸/证件识别。放到 M6 之后按需迭代。

## 2. 原思路逐项评审

### 2.1 总体：方向可行，顺序有误

技术栈本身没有致命错误，问题在**顺序**和**假设**：先选型后验证网络、先写代码后定契约、先做功能后想安全/运维。这会让最贵的返工发生在最晚的时候。

### 2.2 C++ 后端：可行，但你要清楚代价

**能做的部分**：HTTP/WS 服务、JSON、MySQL 访问、文件上传、鉴权，C++ 生态都能覆盖；性能上做这个项目是"杀鸡用牛刀"——瓶颈在网络、图片、数据库，不在 CPU。

**框架选型结论（2026-11 核对）**：**Drogon v1.9.14**（MIT，2026-10-12）。路由/中间件/WebSocket/multipart/ORM/异步 IO 全带，vcpkg 一键装，GitHub CI 有 Windows-2022 MSVC 构建+测试，中文资料多。备选 fallback：**cpp-httplib v0.65.0**（header-only，自带 WS/multipart）+ 同一数据库层。已否决：userver（无 Windows）、oatpp（停滞约 1 年且无官方 MySQL 模块）、Pistache（无 WebSocket）、Boost.Beast（只是协议库，等于自己写半个框架）、cpprestsdk（已归档，vcpkg 端口移除）。

**真实的代价**（调研量化，MVP 口径、不含前端）：

| 环节 | C++/Drogon | Go/Gin | Node/Fastify |
|---|---|---|---|
| 环境 + 工具链 | 1.0~2.0 | 0.5 | 0.5 |
| DB/DAO + 迁移 | 3.0~4.0 | 2.0~2.5 | 2.0~2.5 |
| 鉴权/中间件/校验 | 3.0~4.0 | 1.5~2.0 | 1.5~2.0 |
| 业务状态机/事务 | 3.0~3.5 | 2.5~3.0 | 2.5~3.0 |
| WebSocket 实时 | 1.0~1.5 | 1.0 | 1.0 |
| 上传/静态/文件 | 1.0~1.5 | 0.5~1.0 | 0.5~1.0 |
| 测试 | 2.0~2.5 | 1.5 | 1.5 |
| 服务化/部署 | 1.0 | 0.5 | 0.5 |
| **合计** | **15.5~20 人日** | **10~12 人日** | **10~11.5 人日** |

**结论**：
- C++ 是课程/毕设硬要求或学习目标 → 继续，用 Drogon 把轮子成本降到最低，M0 用 1 天 spike 验证（验收清单见 §4.2），任一关键项卡 >4 小时就触发 fallback。
- 如果目标是"尽快给同学用" → 建议 Go（Gin/Echo）或 Node（Fastify），省约 40% 后端工期；
- **折中**：无论选什么后端，先定 OpenAPI 契约、前端独立开发，后端语言就变成可替换的实现细节。

### 2.3 MySQL：选型正确，但缺四件事（外加一个版本雷）

1. **版本雷**：本机 MySQL 8.0 已于 **2026-04-30 EOL**，不应作为新项目基线 → 直接装 **8.4 LTS**（稳，至 2032-04）或 **9.7 LTS**（新，至 2034-04）。注意 8.4/9.7 默认 caching_sha2_password、mysql_native_password 已移除，C++ 客户端连接要先验证（§4.2 spike 第 6 项）。
2. **Schema 版本管理**：没有迁移机制，改表靠手写 SQL 是事故之源 → 编号 SQL 文件 + schema_migrations 表（§5.7）。
3. **中文检索**：LIKE '%钥匙%' 在 10 万行时明显变慢且无法相关度排序 → MySQL 8 的 **ngram 全文索引**（§5.5）；1 字查询回退 LIKE。
4. **并发约束**：认领的"一物一人"必须靠数据库约束 + 事务，不能"先查再插"（有竞态）。
5. **备份与恢复**：数据库和照片是全部资产，没有备份等于没有项目（§7.5）。另外：**不要把图片存成 BLOB 塞进 MySQL**，数据库存元数据、文件存磁盘。

### 2.4 "行业最新架构"：需要落地成可执行的选型

这四个字至少回答 5 个问题：渲染模式、框架、状态管理、UI 方案、实时方案。原方案一个都没定。定稿如下（版本已核实，完整清单见 §4.9）：

| 决策 | 结论 | 理由 |
|---|---|---|
| 渲染模式 | **SPA，不做 SSR** | 局域网单源、无 SEO、无首屏服务端依赖；SSR 会多一个 Node 常驻进程（本机内存紧张）、双端状态、部署复杂度，收益接近 0 |
| 框架 | **React 19.3.1 + Vite 8.3.6 + TypeScript 6.0.3** | 生态最大（shadcn/TanStack/RHF 全 React 优先）；Vite 8 已用 Rolldown；TS 7 虽 GA 但 typescript-eslint peer 上限 <6.1.0，先锁 6.0.3 |
| 样式/组件 | **Tailwind CSS 4.3.5 + shadcn/ui（Radix 1.8.1）+ lucide-react** | 原子化样式、组件可复制可改；Base UI 仍 1.0.0-rc.0，MVP 不用 |
| 路由/状态 | **TanStack Router 1.170.46 + TanStack Query 5.107.1 + Zustand 5.1.0** | 类型安全路由 + 服务端状态缓存/失效/乐观更新；Zustand 只放 UI 状态 |
| 表单/校验 | **react-hook-form 7.91 + zod 4.6.7** | 发布/认领表单体验与类型校验 |
| PWA | **vite-plugin-pwa 2.0.0**（HTTPS 后启用） | manifest + SW precache + 离线壳 |
| 运行时 | **Node 26.13.0 LTS + pnpm 12.18.0** | 只用于开发构建；生产机只放 dist 产物 |

**移动端策略**：响应式 + PWA，一套代码手机/电脑通用；手机"添加到主屏幕"；拍照走 file input capture（HTTP 可用）→ HTTPS 后切换/补充 getUserMedia 自建相机（可选）。

**两个关键约束（调研核实，直接影响方案）**：
1. secure context 功能分水岭：http://私有IP 下 PWA/SW/getUserMedia/Notification 全禁；capture 拍照可用。iOS 安装必须手动"分享→添加到主屏幕"（Safari 从不触发 beforeinstallprompt）；iOS 通知必须已安装为 PWA（16.4+）。
2. **origin 是 IP 的隐藏坑**：DHCP 换 IP 后 localStorage/cookie/SW 缓存全部作废 → 必须用固定主机名/固定 IP 再谈 PWA（呼应 §7.3）。

### 2.5 本机服务器 + 局域网：方案里最危险的假设

原方案隐含假设"手机连同一个 Wi-Fi 就能访问我电脑上的服务"。**这个假设在校园网里大概率不成立**，原因（本机实测 + 调研）：

1. **AP/客户端隔离**：公共 Wi-Fi 常见配置，同 SSID 设备互不可见（校园网最常见）。
2. **跨 VLAN/三层 ACL**：192.168.1.100/24 是大二层/三层混合网，手机可能落在别的网段。
3. **Portal 认证**：校园 Wi-Fi 是 Open 认证网络，通常有网页认证，且会周期性重认证。
4. **DHCP + MAC 随机化**：IP 会变；手机"私有 Wi-Fi 地址"会触发重新分配/重认证 → 书签/二维码失效。
5. **Public 防火墙**：本机当前网络被识别为"公用"，Windows 默认拒绝入站，必须显式放行。
6. **无线本身**：网卡节能、漫游、2.4G 干扰；笔记本合盖/睡眠直接断服（实测交流电下 3 小时自动睡眠）。
7. **校园网准入（NAC）**：手工配静态 IP 可能被 DHCP Snooping/IP Source Guard 断网 → **严禁在校园网段手配静态 IP**，用路由器 DHCP 保留或向网络中心申请。

**补足**：先做 §7.1 的 5 分钟实测；不可达就用方案 B（自带路由器独立网段，推荐）或 E（隧道兜底）。另外要清醒：**局域网只解决网络位置，不解决安全**——同网段任何设备都能扫描访问你的 API，§8 一条都不能省。

### 2.6 实时交互：语义 + 移动端现实

- 手机浏览器切后台后 **WebSocket 会被挂起/断开**（iOS 尤其严格），回前台必须重新同步。
- 前端方案：**原生 WebSocket + REST**；socket.io 官方 Server 实现列表**没有 C++**，且它不是纯 WebSocket 实现 → 否决。
- 协议要点：心跳 25s（10s 未 pong 判死）、指数退避 0.5→30s（±20% 抖动，稳定 30s 后重置）、事件自增 id + 重连后 GET /api/events?since= 补洞、按 id 去重、跳号则全量拉取。
- **Caddy 重载配置会强制断开所有 WebSocket 连接**（官方文档明确）→ 前端重连逻辑是刚需，不是可选项。
- 移动端恢复：监听 visibilitychange / pageshow.persisted / freeze-resume / online；visible 时"先 REST 拉齐、再订阅"。
- **不要承诺"锁屏也能收到通知"**（除非做 Web Push：iOS 需 A2HS，且 C++ 侧 VAPID 实现成本约 2~4 人日；放 M6+）。

### 2.7 安全与合规：局域网不是安全边界

校园环境里"好奇的同学"比公网攻击者更现实。原方案没有安全设计，至少要补：认证与会话、密码哈希、登录限流、越权（IDOR）防护、上传安全、SQL 注入、CSRF/CORS/CSP、WS Origin 校验、审计日志、MySQL 最小权限；以及**《个人信息保护法》合规**：最小必要、告知同意、脱敏展示、保留期限、删除权、不出境（§8.3）。面向师生提供服务前，建议向学校网络中心/指导老师报备。

### 2.8 工程流程：没有验收标准 = 没有完成

原方案没提需求冻结、API 契约、测试策略、CI、验收清单、运维手册、演示脚本。补足：每个里程碑都有"可演示的验收动作"（§9）、契约先行（§6.4）、验收清单（§10）、运维手册（§7）。

### 4.1 总体架构

设计原则：
- **Caddy 前置**：把 TLS/证书/静态/压缩/安全头从 C++ 剥离，C++ 只做业务 API，代码量和踩坑大减；Caddy 单 exe、Windows 友好。
- **C++ API 只监听 127.0.0.1**，对外只暴露 Caddy 一个端口（8443），攻击面最小。
- **前后端同源**：Caddy 同时提供静态站点和 /api、/ws 反代 → 无 CORS，Cookie 最简单。
- **可迁移**：地址/端口/证书全在配置里，未来迁云只改部署配置。

### 4.2 后端（C++）

| 项 | 选择 | 理由/备选 |
|---|---|---|
| 语言标准 | C++20 | MSVC 支持良好 |
| Web 框架 | **Drogon 1.9.14** | 路由/WS/multipart/ORM/异步 IO 全带，vcpkg 可装，Windows CI 在跑 |
| Fallback | cpp-httplib 0.65.0 + 同一 libmariadb | Drogon 构建失败/阻塞性 bug >1 天时切换；路由改写约 0.5 人日 |
| 数据库客户端 | **libmariadb 3.4.11**（LGPL-2.1，vcpkg） | Drogon 的 mysql 特性在 Windows 上就是拉它；避免 Oracle 客户端的 GPL 解释成本；DLL 可替换即合规 |
| 数据库访问 | 手写 SQL + prepared statement（repository 层） | 可控、防注入；Drogon ORM 可用但不必深度绑定（便于 fallback） |
| JSON | jsoncpp（Drogon 自带）+ nlohmann/json 仅测试/配置 | 避免双 JSON 库来回转换 |
| 日志 | **spdlog 1.17.0**（rotating 10MB×8 + daily sink） | 结构化、滚动、线程安全；合规留存 ≥6 个月靠 daily 归档 |
| 密码哈希 | **libsodium 1.0.22**（Argon2id） | 不自己实现 |
| 测试 | GoogleTest 1.18.0（单元）+ 脚本集成测试 | 状态机、校验器、取件码必须单测 |
| 构建 | CMake ≥3.25 + Ninja + vcpkg manifest | 依赖可复现；锁 baseline |

**CMake/MSVC 关键坑（必须写进脚本）**：
- 必须加 **/utf-8**（中文源码/字符串），/EHsc /W4，C++20；定义 NOMINMAX、WIN32_LEAN_AND_MEAN。
- 动态 triplet 对应 /MD；**不要混用静态/动态 CRT**（LNK2038）。
- 首次构建设 **VCPKG_MAX_CONCURRENCY=2**（本机空闲内存仅 1.66~3GB，并行编译易 OOM）；首次装依赖可能 30~60 分钟（有二进制缓存则几分钟）。
- 构建命令示例：cmake -B build -G Ninja -DCMAKE_TOOLCHAIN_FILE=%VCPKG_ROOT%/scripts/buildsystems/vcpkg.cmake -DVCPKG_TARGET_TRIPLET=x64-windows -DCMAKE_BUILD_TYPE=Release
- 部署时把 drogon.dll、trantor.dll、jsoncpp.dll、mariadb.dll、spdlog.dll 等拷到 exe 旁；**TLS 交给 Caddy，Drogon 不编 OpenSSL**。

**M0 技术验证 spike（1 天，7 项验收）**：
1. vcpkg install 成功（记录耗时）。
2. GET /healthz 返回 200 JSON，**中文不乱码**。
3. 参数化 SQL 建表 + 中文插入/查询。
4. WebSocket echo 收发 100 条。
5. multipart 上传 5MB jpg，校验类型/大小/落盘/返回 URL。
6. **MySQL 8.4/9.7 caching_sha2 连接实测**（非 TLS TCP 可能需要 RSA 公钥交换；失败则启用 MySQL 自签 TLS 或换 Connector/C++）。
7. Ctrl+C 3 秒内干净退出、关闭连接、flush 日志。

**任一关键项卡 >4 小时 → 当天触发 fallback 决策，不拖到第二天。**

**服务化与退出**：WinSW XML 配 depend=MySQL80、stoptimeout 15s、onfailure restart 10s、日志 roll-by-time；Drogon 监听 127.0.0.1:8080；退出时 app().quit() → 关闭连接池 → spdlog::shutdown()；上传先写 .part 再原子改名；提供 --console 模式验证同一路径。

### 4.3 数据层

- **MySQL 8.4 LTS**（推荐，稳，至 2032-04）或 9.7 LTS（至 2034-04）；**不要用已 EOL 的 8.0**。当前 8.0 数据为空，建议卸载后全新安装目标版本，避免跨大版本升级链。
- 字符集 utf8mb4、排序规则 utf8mb4_0900_ai_ci。
- 时区：**数据库存 UTC**，API 返回 ISO8601，前端按 Asia/Shanghai 展示。
- InnoDB；关键处显式 SELECT ... FOR UPDATE；事务短小。
- 账号：应用专用账号仅 SELECT/INSERT/UPDATE/DELETE；迁移用独立 DDL 账号；root 仅 localhost；bind-address=127.0.0.1；skip-name-resolve、local_infile=OFF；执行 mysql_secure_installation。
- 连接池 10~20；开发期 5。
- 本机参数建议：innodb_buffer_pool_size=512M、performance_schema=OFF、max_connections=100（内存紧张）。
- **binlog 开启**（PITR 备份用）：log_bin、binlog_expire_logs_seconds=1209600。

### 4.5 实时方案

- 原生 WebSocket（Drogon 内置），不用 socket.io（无 C++ 官方实现）。
- 连接：同源 wss://<host>/ws；握手 Cookie 鉴权 + Origin 精确白名单（防 CSWSH）；不用 URL 带 token（会进日志）。
- 心跳：客户端 25s ping，服务端 pong；10s 未收判死；服务端清理 60s 无数据连接。
- 重连：0.5→1→2→4→8→16→30s，±20% 抖动，稳定 30s 重置；online/页面可见/bfcache 恢复立即触发。
- 事件：自增 id；客户端存 lastEventId；重连后 GET /api/events?since=<id>&limit=100 补齐；按 id 去重；跳号则全量拉当前页。
- 移动端恢复：visible 时先重连、再并发拉未读数与事件增量、最后刷新 badge；**"先拉后订阅"**。
- 鉴权：每 30 分钟重校验会话；登出立即关闭该用户全部连接。
- Web Push：M6+ 可选（iOS 需 A2HS，C++ 实现 VAPID 约 2~4 人日）。

### 4.6 图片与文件

- **客户端压缩流水线**：选图/拍照 → 校验（jpeg/png/webp，≤5MB）→ >300KB 或长边>1600 才压缩 → createImageBitmap（EXIF 自动摆正）→ 长边 1600 → toBlob WebP q0.8（不支持时回落 JPEG q0.82）→ 目标 ≤400KB → 同时生成 640px 缩略图。
- **上传**：FormData multipart（file + thumb）+ XHR 进度（fetch 无上传进度）+ Idempotency-Key；失败退避重试 2 次；并发 2；per-file 状态机。
- **HEIC**：accept 排除 image/heic（iOS 拍照必转 JPEG；macOS Safari 靠 accept 触发转换）；检测到 HEIC 提示转格式，不引 heic2any。
- 服务端：白名单 + **Magic bytes** 校验 + 尺寸上限 + 随机 UUID 文件名 + 存 webroot 外 + 私有目录不放静态路径；公开图由 Caddy /media/ 直出（UUID 不可枚举），认领凭证等私密图走 API 鉴权。
- **EXIF/隐私**：客户端重编码已剥离元数据；服务端在 M4 安全加固阶段用 libvips 重编码兜底（若 vcpkg 集成顺利），并纳入"上传图 EXIF/GPS 已剥离"验收。
- 清理：孤儿文件每日清理；证件/人脸类按审核结果删除；已完成 30 天后删凭证图。
- **禁止**：图片存 DB BLOB、原始文件名、SVG（XSS）、可执行目录。

### 4.7 认证与会话

- **服务端 Session**：Cookie 名 **__Host-lf_sid**（HttpOnly + Secure + SameSite=Lax + Path=/，无 Domain）；token 只存 SHA-256；登录后重新生成；空闲 30 分钟 / 绝对 12 小时过期；登出即失效；管理员可踢下线。
- 密码：**Argon2id**（libsodium crypto_pwhash_str，建议 m=32MiB、t=3、p=1；OWASP 最低 19MiB/t=2）。
- 注册：**学号 + 邀请码**（管理员生成，限时限次）；登录失败渐进延迟 + 限流（5 次/分/IP、10 次/时/账号）+ 锁定。
- CSRF：SameSite=Lax + 双提交 token（所有非 GET）+ 校验 Origin/Referer；WS 握手同样校验 Origin。
- 管理员：独立强口令 + TOTP 二次验证；管理入口用 Caddy remote_ip 限制仅本机/运维网段；首登强制改密。
- 不选 JWT 的原因：单机同源场景无法即时吊销、泄露后有效期内一直可用、SPA 存 localStorage 更易被 XSS 窃取。

### 5.2 认领的并发控制（关键设计）

**规则**：一个帖子同一时刻最多一个"有效认领"（pending/approved）。

MySQL 8 没有部分索引，用**生成列 + 唯一索引**实现：

~~~sql
ALTER TABLE claims
  ADD COLUMN active_item_id BIGINT
    GENERATED ALWAYS AS (IF(status IN ('pending','approved'), item_id, NULL)) STORED,
  ADD UNIQUE KEY uk_claims_active_item (active_item_id);
-- 唯一索引允许多个 NULL，因此已结束的认领互不冲突
~~~

认领事务：

~~~sql
START TRANSACTION;
SELECT id, status, user_id, expires_at FROM items WHERE id=? FOR UPDATE;  -- 行锁
-- 校验：非本人帖子、未过期、无有效认领
INSERT INTO claims(item_id, claimant_id, status, answer, message)
  VALUES (?,?,'pending',?,?);
-- 并发插入触发唯一冲突 1062 → 回滚并返回 409
UPDATE items SET status='claim_pending', updated_at=NOW(3) WHERE id=?;
INSERT INTO events(type, user_id, entity_type, entity_id, data_json) VALUES (...);
COMMIT;
~~~

失败语义：唯一冲突 → 409 CLAIM_CONFLICT（"手慢了，已有其他同学申请"）。
审核通过：锁 claims 行 + 事务内生成 6 位取件码（存哈希、24h 过期），items→claim_approved，其他 pending→rejected。
完成：拾得者核销取件码 + 失主确认，双方都完成才 items→completed。

### 5.3 状态机

~~~
items:   open ──(有人认领)──> claim_pending ──(通过)──> claim_approved ──(交接完成)──> completed
           │                      │  ▲                     │
           │                      │  └──(拒绝/取消)────────┘
           ├──(管理员下架)──> removed
           └──(30 天到期)──> expired ──(续期)──> open

claims:  pending ──(通过)──> approved ──(核销+双方确认)──> completed
            ├──(拒绝)──> rejected
            ├──(申请人取消)──> cancelled
            └──(24h 未审核)──> expired
~~~

所有跃迁在服务层集中校验 canTransition(from,to,actor)，非法跃迁 409；状态机每个非法组合都要单元测试。

### 5.4 事件、通知与补偿

- 业务事务内写 events 行（公开事件 user_id=NULL，定向事件写收件人）；提交后推送 WS；推送失败不影响业务。
- 客户端断线重连用 GET /api/events?since= 补齐（只返回公开事件 + 自己的定向事件）；events 保留 7 天，过期清理。
- 通知写入 notifications（带 event_id 便于去重）；未读数直接 SQL COUNT + 缓存可选。
- 事件只做"提示 + 让前端重新拉取"，**不把事件当唯一数据源**，丢事件也不会数据不一致。
- 每日定时任务：过期归档、取件码过期、到期提醒、孤儿文件清理；备份走 Windows 计划任务（更稳）。

### 5.5 中文检索

~~~sql
ALTER TABLE items
  ADD FULLTEXT INDEX ft_items_title_desc (title, description) WITH PARSER ngram;

SELECT ... FROM items
WHERE MATCH(title, description) AGAINST (? IN BOOLEAN MODE)
  AND status='open' AND type=?
LIMIT 20;
-- 1 个字：回退 LIKE '%字%'（数据量小可接受）
~~~

注意：ngram 默认 ngram_token_size=2（改需重启）；结果按相关度 + 时间混合排序；前端输入防抖 300ms；不要每次按键都打全文检索。

### 5.6 容量与归档

- 图片：客户端压缩后 100~400KB/张，200 张/天 → 20~80MB/天 → 每年 7~30GB。D 盘 90GB 可用约 2~3 年。
- 策略：原图保留 90 天 + 缩略图长期；已完成/过期原图归档到移动硬盘/NAS/网盘；每日巡检磁盘 <15% 告警。
- 数据库：3 年百万级以内单表无压力；audit_logs 保留 ≥6 个月（合规），notifications 90 天，events 7 天。
- 目录：D:\data\lostfound\{public,private}\yyyy\mm\uuid.ext；不要放系统盘；备份到另一块物理盘。

### 5.7 迁移机制

- backend/sql/0001_init.sql、0002_xxx.sql 编号递增；schema_migrations 记录版本；

## 7. 部署与网络方案（结合本机实测）

### 7.1 第 0 步：5 分钟网络可达性实测（今天就做）

~~~powershell
# ① D:\tmp 放 hello.txt，起临时 HTTP 服务（本机已装 Python）
cd D:\tmp; python -m http.server 8000 --bind 0.0.0.0
# ② 另开【管理员】PowerShell 放行 Public 入站（只加一条，测完删）
New-NetFirewallRule -DisplayName "lan-test-8000" -Direction Inbound -Protocol TCP -LocalPort 8000 -Action Allow -Profile Public
# ③ 手机连同一 Wi-Fi，浏览器访问 http://192.168.1.100:8000/
# ④ 成功时 ① 窗口会打印手机 IP；无任何日志=被上游拦截
Remove-NetFirewallRule -DisplayName "lan-test-8000"
~~~

| 现象 | 判定 | 下一步 |
|---|---|---|
| 能打开且日志出现手机 IP | 无隔离，方案可行 | 继续 §7.2，先解决 IP 漂移 |
| 超时/拒绝，换 8443/80/443 均不通 | 客户端隔离或跨 VLAN | 走 §7.2 方案 B/E |
| 8443 通、80/443 不通 | 仅端口策略拦截 | HTTPS 用 8443；证书走 DNS-01（不依赖入站） |
| 手机 IP 不在 10.40/16 | 不同网段/NAT | 换同段设备复测或方案 B |
| 能通但频繁掉线 | Portal 超时/MAC 随机化 | 关手机"私有 Wi-Fi 地址"，关网卡节能（§7.4） |

注意：
- **手机禁 ICMP 是常态，不要用 ping 判死**；以 HTTP 日志/服务端 Get-NetTCPConnection 为准。
- 测试前关掉 VPN/代理；本机有 3 张 VMware 虚拟网卡，确认服务绑定与防火墙规则覆盖 WLAN。
- 分别测 80/443/8443/9443 四个端口，记录哪些手机能连通（决定对外端口）。

**判定结论直接决定方案**：
- 通 + 能买域名 → 方案 A（域名 + DNS-01，体验最好）。
- 通 + 不买域名 → 方案 A'（Caddy 内部 CA + 装根证书）。
- 不通 → 方案 B（自带路由器独立网段，**推荐兜底**）；只 1~2 人演示可用手机热点；跨网演示用 Tailscale/Cloudflare Tunnel。

### 7.2 三套拓扑

| 方案 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **B 自带路由器（推荐兜底）** | 旅行/家用路由器建私有网段（如 192.168.8.0/24），本机有线/USB 网卡接 LAN，IP 固定；手机连该路由 Wi-Fi | 完全可控、无 AP 隔离、IP 固定、易加 UPS | 仅覆盖该 Wi-Fi；上行接校园网仍需 Portal | 答辩/试运行/宿舍小范围 |
| **A 校园 Wi-Fi 直连** | 本机+手机同 SSID 直连 | 零成本、覆盖广 | 依赖校园网隔离策略、IP 漂移、Public 防火墙 | 仅当 §7.1 实测通过 |
| **E 隧道/热点（跨网兜底）** | 手机热点同 NAT；或 Tailscale（每台设备装客户端）；或 Cloudflare Tunnel（仅演示，真实数据不出境） | 绕过隔离与跨网、自带可信 HTTPS | 每台设备装客户端/依赖第三方；CF 有数据出境合规问题 | 远程运维、跨网演示 |

**决策树**：实测通 → A/A'；实测不通 → B（若只演示 1~2 人则 E）。**架构不改**：同源相对路径 API、配置化地址，三套只改部署配置。

### 7.3 HTTPS 方案（必做）

| 方案 | 手机是否受信 | 前置条件 | 工作量 | 结论 |
|---|---|---|---|---|
| 自签证书 | ❌ 每次警告，SW/PWA 不可用 | 无 | 0.5h | **否决**（训练用户忽略警告，更糟） |
| mkcert | 需装 rootCA | 每台设备装根证书 | 0.5~1h/人 | 备选（项目 2022 后停更，可用 Caddy 替代） |
| **Caddy 内部 CA** | 需装 rootCA | Caddy tls internal | 本机 10min + 每设备 10min | **零成本首选** |
| **真域名 + DNS-01** | ✅ 公共 CA，零设备配置 | 域名（¥30~100/年）+ 可编程 DNS | 2~4h | **正式首选** |
| Cloudflare Tunnel | ✅ | CF 账号+域名 | 1h | 仅公网演示（数据出境风险） |
| Tailscale（ts.net） | ✅ | 每台设备装客户端 | 1~2h | 运维/跨网兜底 |

**推荐路线（正式首选）**：买一个域名 → 公共 DNS 加 A 记录直接指向内网 IP（如 lost.example.com → 192.168.1.100）→ Let's Encrypt **DNS-01** 签证书（只校验 DNS TXT，**无需 80/443 入站**；本机实测 ACME 443 出站可达）→ Caddy 用证书。实现二选一：
1. 从 caddyserver.com/download 勾选 DNS 插件生成 Windows 单文件（免装 Go）；
2. 用 win-acme 跑 DNS-01 出 PEM，Caddy 用 tls cert.pem key.pem 加载（续期靠计划任务）。

**零成本备选（内部 CA）**：
- Caddy 配 tls internal；本机 caddy trust 自动装入 Windows 信任库；其他设备装 Caddy 数据目录 pki/authorities/local/root.crt。
- **证书 SAN 必须含实际访问的 IP/域名**（Caddy 按 site address 自动生成 IP SAN）；根证书私钥只在本机，勿外发。
- iOS：Safari 打开 root.crt → 设置顶部"已下载描述文件"→ 安装 → **设置→通用→关于本机→证书信任设置→开启完全信任**（漏这步不生效）。
- Android 7+：设置→安全→加密与凭据→安装证书→CA 证书；坑：用户 CA 默认不被 App/WebView 信任，但 Chrome 上网可以；装完重启浏览器。
- Windows：certutil -addstore -root root.crt（或双击安装到"受信任的根证书颁发机构/本地计算机"）。
- Firefox 独立信任库：security.enterprise_roots.enabled=true 或手动导入。
- **HSTS 慎用**：内部 CA + 长 max-age 一旦证书出问题会把自己锁在门外；HTTPS 稳定后再开短 max-age。

**其他硬性要求**：对外一律 HTTPS，HTTP 仅本机回环调试；页面内不得出现 ws://（混合内容会被拦）；证书过期/换机后所有设备要重装（内部 CA 路线）。

- 电池当 UPS：断电可撑 1~3 小时；设低电量 20% 休眠/关机防硬断电；长期插电用 Lenovo Vantage 保养模式（~60%）；宿舍断电频发可加 500VA UPS（约 ¥300~500）。

**服务化 + 自启 + 自愈**（三件套）：
- 三个常驻进程都用 **WinSW 2.12.0** 包服务：caddy、lostfound-api；MySQL80 官方服务改 Automatic。
- 每个配 onfailure action="restart" delay="10 sec"、启动类型 Automatic (Delayed Start)；**MySQL 先起、API 后起**（WinSW depend 或脚本重试）；Caddy 最后。
- Caddy 改配置用 caddy reload（Windows 服务本身不能 reload，只能 restart）；Caddy 数据目录用 storage 指到 D 盘固定路径（避免升级/换用户丢 CA 与证书缓存）。
- 健康检查：计划任务每 5 分钟 GET https://127.0.0.1:8443/healthz（内含 DB ping），失败重启服务 + 告警（企业微信/钉钉机器人）。
- **不要选 NSSM**（2014 年停更，Win10+ 还需预发布版）。

**Windows Update / Insider（最大黑天鹅）**：
- 家庭版无组策略：设置活动时间 + 暂停更新（最多 5 周）+ 周日固定维护窗口主动更新重启。
- **本机是 Insider Preview 26220（Dev/Beta 通道），会频繁推 build 并可能强制重启**：正式运行前停止获取预览版；若 build 已高于正式版，只能等正式版追平或重装 → 试运行机不要留在 Insider。
- 兜底：所有服务自启 + 开机自检 + 恢复后自动推送"已恢复"通知，被重启也能 5 分钟内恢复。

**远程维护（家庭版限制）**：Windows 11 家庭版**不能做 RDP 服务端**（微软文档明确）。用 OpenSSH Server 可选功能 + Tailscale/ZeroTier 组网后 SSH；图形化用 RustDesk/ToDesk/向日葵；或升级 Pro 用 RDP（绑 Tailscale 网段，不暴露公网）。最小权限：单独运维账号 + 公钥登录 + 禁密码登录。

**资源预算（13.85GB 总量、实测空闲曾只有 1.66GB）**：

| 常驻项 | 目标占用 | 措施 |
|---|---|---|
| Windows 基线（Defender/VMware/输入法） | 5.5~7GB | 关 VMware 自启、OneDrive、Xbox/Game Bar、Edge 后台 |
| MySQL 8.4 | 0.5~0.8GB | innodb_buffer_pool_size=512M、performance_schema=OFF、max_connections=100 |
| C++ API + Caddy | 0.2~0.4GB | 线程池 8~12；DB 连接池 ≤20 |
| 备份/监控脚本 | 0.1GB 峰值 | 计划任务短时运行、错峰 |
| 预留 | ≥2GB | 否则 MySQL OOM/系统卡顿 |

合计约 7~9GB 常驻 → **开服前必须先清启动项**；前端构建（Node 峰值 1~2GB）只在开发时做，生产机只放 dist 产物；vcpkg 编译设 VCPKG_MAX_CONCURRENCY=2。

### 7.5 备份与恢复（不做 = 项目随时归零）

**数据库**（每日 02:00 计划任务）：

~~~powershell
& "C:\Program Files\MySQL\MySQL Server 8.4\bin\mysqldump.exe" --defaults-extra-file=D:\ops\backup.cnf --single-transaction --quick --routines --triggers --events --set-gtid-purged=OFF lostfound | & "C:\Program Files\7-Zip\7z.exe" a -si -t7z -mhe=on -p"$env:BK_PASS" D:\backup\db_$(Get-Date -f yyyyMMdd).sql.7z
~~~

- **binlog 增量**（PITR）：my.ini 开 log_bin + binlog_expire_logs_seconds=1209600，每 15 分钟归档 → DB RPO ≤15 分钟。
- 备份账号最小权限：SELECT, LOCK TABLES, SHOW VIEW, EVENT, TRIGGER, PROCESS；文件加密 + ACL 仅管理员；**绝不把明文 dump/照片放网盘**。
- **图片**：每小时 robocopy 到**另一块物理盘**（同盘不算备份）；每周加密后拷离线移动硬盘/异机。
- **配置与证书**一起备份（Caddyfile、my.ini、scripts、Caddy 数据目录含内部 CA）；**根证书私钥单独离线保存**。
- 保留：日备 7 份 / 周备 4 份 / 月备 12 份；图片随信息生命周期。
- **恢复演练**：每月建 lostfound_restore 库 → 解压导入 → 校验行数/最新时间戳/随机 3 张图片可打开 → 记录耗时（RTO ≤2h）。
- 不选 XtraBackup：8.0 线已 EOL 且无官方 Windows 二进制；本项目数据量小，mysqldump + binlog 足够。

### 7.6 日志与监控

- 应用日志：spdlog rotating 10MB×8 + daily sink；含 requestId、userId、路由、状态码、耗时；按天归档保留 ≥6 个月（合规），业务日志 14 天。
- Caddy access log（JSON）保留 14 天；MySQL 慢查询（>200ms）每周检查。
- /healthz 检查 DB ping + 磁盘余量 + 进程自身；每日巡检脚本输出磁盘/内存/错误日志/备份是否成功；磁盘 <15% 告警。
- 审计日志 audit_logs 仅 INSERT（应用账号无 UPDATE/DELETE 权限），每日导出，留存 ≥6 个月。
- 可选：Uptime Kuma（另一台设备）或服务器宕机短信/微信告警。

### 7.7 Caddyfile 样例（内部 CA 版；真域名改 tls 段）

~~~caddyfile
{
  storage file_system D:\campus-lostfound\ops\caddy-data
  admin 127.0.0.1:2019
}
https://192.168.1.100:8443 {

  encode zstd gzip
  header {

    X-Frame-Options DENY
~~~

## 8. 安全与合规基线

### 8.1 威胁模型（局域网 ≠ 安全）

| 威胁 | 场景 | 防护 |
|---|---|---|
| 未授权访问 | 同网段任何人扫端口调 API | 会话鉴权 + 全部接口默认拒绝 + 限流 |
| 越权（IDOR） | 改 URL 里的 id 看别人认领/凭证 | 每个资源做 owner/admin 校验 + 对外 UUID + 集成测试 |
| 撞库/爆破 | 学号可猜 | 邀请码注册 + 登录限流/锁定 + Argon2id |
| 恶意上传 | 传 HTML/SVG/超大文件/图片马 | Magic bytes + ≤5MB + 禁 SVG + 私密目录 + 重编码 |
| SQL 注入 | 搜索/筛选参数 | 全部 prepared statement + 输入校验 |
| XSS | 帖子内容/昵称 | React 默认转义 + CSP + 禁止 dangerouslySetInnerHTML |
| CSRF/CORS | 第三方页面构造请求 | SameSite=Lax + 双提交 token + Origin 校验；生产同源 |
| WS 劫持 | 恶意页面连你的 WS | 握手校验 Origin 精确白名单 + Cookie |
| 数据泄露 | 手机号/学号被爬 | 默认脱敏 + 权限分级 + 审计 + 禁止批量导出 |
| 服务被刷 | 脚本刷帖/刷图 | 发帖/上传限流 + 可选人机校验（M5+） |
| 物理/系统 | 电脑被室友操作 | 锁屏 + 管理员密码分离 + DB 只本机 |

### 8.2 上线前安全检查表（必须全绿）

- [ ] 全站 HTTPS（HTTP 仅回环），证书 SAN 含实际访问地址；页面无混合内容
- [ ] Cookie：__Host-lf_sid，HttpOnly + Secure + SameSite=Lax + Path=/；登出即失效；空闲/绝对过期生效
- [ ] 密码 Argon2id（m=32MiB,t=3,p=1）；日志无明文密码/token
- [ ] 登录/注册/发帖/上传/搜索接口限流；失败锁定
- [ ] 所有 SQL prepared statement；无字符串拼接；错误响应不泄露 SQL/堆栈/路径
- [ ] 上传：白名单 + magic bytes + ≤5MB + UUID 文件名 + webroot 外 + 私密图走鉴权；EXIF/GPS 已剥离（或 M4 前记录残余风险）
- [ ] 越权测试：A 用户改 B 的帖子/认领/查看凭证 → 403/404
- [ ] CSRF 双提交 token + Origin/Referer 校验；WS Origin 校验
- [ ] 安全头：CSP、X-Content-Type-Options、Referrer-Policy、X-Frame-Options、Permissions-Policy；HSTS 稳定后再开短值
- [ ] 管理后台独立鉴权 + TOTP + remote_ip 限制 + 操作全审计
- [ ] MySQL：应用账号仅 CRUD、root 仅 localhost、bind 127.0.0.1、skip-name-resolve、local_infile=OFF、无匿名用户/test 库
- [ ] 审计日志仅 INSERT、留存 ≥6 个月、每日导出
- [ ] 备份加密、权限仅管理员、恢复演练通过
- [ ] 无硬编码密钥/后门；依赖无已知高危（npm audit、vcpkg 清单锁版本）
- [ ] 隐私政策/免责声明上线；注册有同意留痕；公开页无完整手机号

### 8.3 隐私与合规（中国《个人信息保护法》等）

| 要求 | 依据 | 本项目落地 |
|---|---|---|
| 最小必要、目的限定 | PIPL 第 5/6 条 | 字段白名单：学号、姓名、学院、联系方式（可选）、物品类别/描述/照片；**不采集身份证、人脸、精确位置**（上传剥离 EXIF 坐标） |

| 保留与删除 | PIPL 第 19/47 条；《网络数据安全管理条例》第 9 条 | 招领信息 30 天归档/学期末清理、认领记录 1 年、日志 ≥6 个月、注销后 30 天内删除；用户可删除发布/注销账号，30 天内处理并留痕 |

| 事件处置 | 《网络数据安全管理条例》第 10/11 条 | 泄露等事件按规定 24 小时内报告主管部门并通知利害关系人；保留处置记录 |
| 免责与报备 | 平台自律；网络安全法第 21 条（等保、日志 6 个月） | 免责声明（仅信息撮合、不保管物品、不担保真实性、冒领自负法律责任、管理员有权删除）发布须知+页脚双处；上线前向学校信息化/网安部门**提交备案**（用途、域名/IP、数据字段、访问范围），按学校要求做等保（通常二级）；若映射公网或用学校域名，走统一 ICP 备案审批 |

### 10.3 非功能（含调研给出的量化指标）

- **前端质量（p75，局域网真机）**：LCP ≤2.5s、INP ≤200ms、CLS ≤0.1；首屏 JS gzip ≤250KB、单路由 chunk ≤120KB；列表滚动 ≥55fps；图片占位→显示 P95 ≤400ms；WS 通知到 UI P95 ≤1s；断线重连 ≤3s 且成功率 ≥99%；拍照→预览 ≤1s；压缩后 ≤400KB；控制台 0 error。上线前在手机/PC 各查一次 window.isSecureContext 与 navigator.mediaDevices。
- **网络**：同 SSID 手机开登录页；重启路由器/重连后 IP 变化书签仍可用；断开校园网后本机内网仍可访问（方案 B）；跨楼/异网段按预期被拒；连续 30 分钟 WSS 不掉线（掉线自动重连）。
- **HTTPS**：手机 Chrome/Safari 无证书警告；SAN 含实际地址；删证书后自动重签；无混合内容；HTTP 正确跳转或不可达；Firefox 无告警。
- **安全**：未登录 API 全 401；改他人 id 越权失败；上传 .php/.svg/改扩展名/超大文件被拒；上传图 EXIF 已剥离；连续错误登录触发限流；SQLi 探测返回统一错误；响应头齐全；审计日志含登录/管理/删除且不可改。
- **备份恢复**：从最近备份恢复行数一致；binlog 可恢复到删除前；随机 10 张图片可打开；恢复总耗时 ≤2h；备份加密、权限仅管理员；异机副本可独立启动。
- **运维**：拔电后靠电池继续服务；强制重启后 5 分钟内服务自动恢复并告警；合盖/关屏不影响；kill 进程 10 秒内自动拉起；Windows Update 重启后自检通过；远程 SSH 仅从 Tailscale 网段可连。
- **性能**：列表/搜索 P95 <500ms（1 万条）；50 并发压测 1 分钟无错误；首屏 <2.5s。
- **兼容性**：iOS Safari、Android Chrome、桌面 Chrome/Edge、微信内置浏览器（提示用外部浏览器打开，PWA 不支持）。

## 12. 现在不要做的事（避坑清单）

1. ❌ 不要先用 http://IP:端口 给手机用——PWA/离线/相机/通知会静默失败（用 file input capture 可临时拍照）。
2. ❌ 不要假设"连同一个 Wi-Fi 就能互访"——先实测。
3. ❌ 不要先后端再前端——先契约后并行。
4. ❌ 不要把图片存进 MySQL BLOB。
5. ❌ 不要用 offset 深分页、不要用 LIKE '%x%' 做全站搜索（量大后）。
6. ❌ 不要用 root 连数据库、不要把密钥/证书提交到 Git。
7. ❌ 不要在没备份的情况下录真实数据。
8. ❌ 不要先做聊天、地图、AI 匹配、积分这些"锦上添花"。
9. ❌ 不要承诺"锁屏也能实时收到通知"（除非做 Web Push + HTTPS + PWA）。
10. ❌ 不要在校园网段手配静态 IP（易被 NAC 断网），用路由器 DHCP 保留或申请固定 IP。
11. ❌ 不要把正式运行机留在 Windows Insider 通道。
12. ❌ 不要用"能跑"当验收——每个 M 要能演示、能回归。

## 附录 D：本方案的已知局限

1. **单机 + 笔记本 + 无线**：达不到 99.9% 可用性；断电、睡眠、Windows Update、Insider 强制重启都会中断；只能做到"自动恢复 + 备份兜底"。
2. **校园网不确定性**：AP 隔离/端口策略无法远程验证，必须现场实测；若不通，方案降级为自带路由器（覆盖范围变小）或隧道（依赖第三方/可能出境风险）。
3. **内部 CA 路线**：每台手机都要装根证书，Android 用户 CA 在部分 App 内不被信任；证书换机需重装。真域名 + DNS-01 可避免此问题（推荐）。
4. **C++ 开发效率**：比 Go/Node 多 5~8 人日；本机内存紧张，vcpkg 首次构建可能 OOM，需要降并发。
5. **移动端推送**：MVP 不承诺锁屏推送；Web Push（尤其 iOS）留到 M6，且 iOS 需安装 PWA。
6. **防冒领是流程+人工**：系统能降低冒领概率（核验问题/取件码/留痕），但不能 100% 杜绝；仍需拾得者/管理员确认。
7. **合规需校方确认**：涉及师生个人信息与校园网服务，上线前应向学校主管部门报备，按学校要求做等保/备案；本文只给工程侧落地建议，不构成法律意见。
8. **数据保留与删除**：需指定负责人执行到期清理与用户删除请求，否则合规承诺落空。
